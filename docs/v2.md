# Moving from Nalim v1 to v2

Here **v1** means the jar on [preserved `main` at `d367a5e`][v1]; **v2** means
[the shipped jar at `84fb642`][v2]. The library versions are
`1.2.0-patched-autoinline` and `1.2.5-patched-autoinline`, respectively.

## Can I keep my bindings?

Yes, if they use the existing public `one.nalim` binding API, the native
signatures match, and the target ABI and JVM are supported. The two jars have
the same method descriptors for `Linker.loadLibrary`, `findAddress`,
`linkClass`, both `linkMethod` and `installCode` overloads, and the two link
counters. A compiled client using those methods needs no recompilation just
to replace the jar. `@Library`, `@Link` (including `name` and `naked`),
`@Code` and `@FieldOffset` were already in v1; keep the same imports. Direct
jumps and automatic copying of small AMD64 functions also predate v2.

Check the **native** side separately:

- Use ordinary `@Link` for a C ABI function. `naked = true` means its target
  expects HotSpot's compiled Java calling convention. It receives the original
  references, even in stack slots, not pointers to array data or selected
  fields. Remove `naked = true` if the target is actually an ordinary C function.
- On AMD64, declare the actual return width: `byte` and `short` sign-extend;
  `char` and `boolean` zero-extend (`boolean` expects 0 or 1 in the low byte).
  V1 already normalized narrow results when all arguments fit in registers.
  The v2 SysV bridge also forwards spilled primitive arguments, including a
  mix of integer and floating-point arguments. Ordinary SysV bindings still
  cannot convert spilled references to native pointers. See [NarrowReturnTest](../test/NarrowReturnTest.java).
- On AArch64, narrow native returns are still unsupported. For a portable
  binding, export a wrapper with a matching full-width return type and convert
  in Java; don't just redeclare an existing narrow C return as Java `int`.
  Raw `@Code` bodies must still match the target ISA and Java calling convention.

## Optional: use a typed intrinsic

V2 adds `Linker.findIntrinsic(String, MethodType)`. On Linux AMD64 it can return
an exact Java `MethodHandle` for a recognized pure integer function. It matches
instructions, not names. Supply the real ABI shape: one or two `int` arguments
returning `int`, or the same shapes entirely in `long`. Load the library first
and keep its code stable. An unknown body, unavailable procfs access, another
platform or `-Dnalim.noinline=true` gives an empty result, not a native handle.

The repository's [`raw_add` fixture](../test/nalim_bench.c) exports unsigned
32-bit addition. Save this as `Maths.java` next to `nalim.jar`:

```java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodType;
import one.nalim.Link;
import one.nalim.Linker;

public class Maths {
    @Link(name = "raw_add") private static native int nativeAdd(int x, int y);
    private static final MethodHandle ADD;

    static {
        Linker.loadLibrary("nalim_bench");
        ADD = Linker.findIntrinsic("raw_add",
                MethodType.methodType(int.class, int.class, int.class)).orElse(null);
        if (ADD == null) Linker.linkClass(Maths.class);
    }

    static int add(int x, int y) throws Throwable {
        return ADD == null ? nativeAdd(x, y) : (int) ADD.invokeExact(x, y);
    }

    public static void main(String[] args) throws Throwable {
        System.out.println((ADD == null ? "@Link" : "intrinsic") + ": " + add(19, 23));
    }
}
```

From the repository root on Linux x86-64 with JDK 25:

```sh
cc -O2 -shared -fPIC test/nalim_bench.c -o libnalim_bench.so
javac -cp nalim.jar Maths.java
java --add-modules=jdk.internal.vm.ci --add-opens=java.base/java.lang=ALL-UNNAMED \
     --enable-native-access=ALL-UNNAMED -Djava.library.path=. -cp nalim.jar:. Maths
```

`intrinsic: 42` means Nalim recognized the compiled function. `@Link: 42` is
the normal fallback for an unrecognized body. Add `-Dnalim.noinline=true`
before `-cp` to exercise that path deliberately.

The lookup itself does not install or replace the native method. Direct use
of this API requires v2. For one client binary that must also run with v1,
[BenchLeafCalls](../test/BenchLeafCalls.java) shows discovery by reflection
once at setup and a typed handle to the linked method as the fallback.

## Platform and runtime differences

- **AMD64 copying:** Ordinary bindings on Linux can recognize additional small
  scalar and memory operations without opting into the handle API. V2 leaves
  loads of writable native globals in native code instead of patching published
  code. Inline counts can therefore change while calls continue to observe
  native updates. See [RebaseProbeTest](../test/RebaseProbeTest.java).
- **Win64:** Ordinary calls still use a real frame with 32 bytes of shadow space;
  that frame is not new. V2 changes how the adapter moves mixed integer and
  floating-point arguments into Win64 positional slots. Keep the C prototype
  and ordinary `@Link`; don't switch to `naked` to avoid the frame.
- **AArch64:** V2 packs spilled arguments for Darwin's fixed-prototype ABI and
  installs an executable entry barrier when HotSpot requires one. The
  [platform fixture](../test/PlatformAbiTest.java) covers mixed spills and calls
  from compiled Java before and after relinking and GC.
- **Target selection:** V2 accepts x86-64 Linux, macOS and Windows, and AArch64
  Linux and macOS. Other pairs are rejected rather than guessed; in particular,
  v1's RISC-V emitter is gone. See [PlatformSelectionTest](../test/PlatformSelectionTest.java).
- **HotSpot:** V2 uses absolute native targets instead of relative foreign jumps
  on pre-17 JVMCI. The [platform workflow](../.github/workflows/platforms.yml)
  has separate Linux x64 smoke cases for JDK 11 and 17; this is not a guarantee
  for every JDK and ABI. A runtime without `jdk.internal.vm.ci` cannot use Nalim.
